# Jinx Data — پنل مرکزی مدیریت و ادغام اشتراک

نسخهٔ فعلی یک پیاده‌سازی توسعه‌ای چندبخشی است که API، مدل داده، صف Outbox، همگام‌سازی مصرف، توکن اشتراک، خروجی‌های اولیهٔ چند کلاینت، داشبورد React و استقرار Docker را کنار هم قرار می‌دهد. **این نسخه هنوز پذیرش تولیدی همهٔ فازهای پرامپت اصلی را پاس نکرده است.** پیش از اتصال به سرویس واقعی و ارائه به مشتری، بخش‌های «محدودیت‌های فعلی» را بررسی کنید.

## نصب سریع (روی سرور اوبونتو/دبیان، با کاربر root)

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/ParvaneZone/ParvMarz/main/install.sh)
```

اسکریپت در صورت نیاز Docker را نصب می‌کند، نام‌کاربری/رمز مدیر و پورت را می‌پرسد (یا خودش می‌سازد)، رازهای تصادفی قوی تولید می‌کند و پنل را بالا می‌آورد. سپس `http://IP:8000/dashboard/` را باز کنید. به‌روزرسانی: همان دستور با `update` در انتها. مسیر نصب: `/opt/parvmarz`.

## اجرا با Docker (فقط Docker لازم است)

```bash
cp .env.example .env      # اختیاری؛ بدون آن هم بالا می‌آید
docker compose up -d --build
```

- کلیدهای `JWT_SECRET`، `SUBSCRIPTION_HMAC_KEY` و `CREDENTIALS_ENCRYPTION_KEY` اگر خالی/placeholder باشند در اولین اجرا خودکار ساخته و در volume داده (`/app/data/secrets.json`) ذخیره می‌شوند؛ نیازی به `python`/`openssl`/`parvmarz` روی میزبان نیست.
- اگر `INITIAL_ADMIN_USERNAME` خالی باشد `admin` و اگر `INITIAL_ADMIN_PASSWORD` خالی باشد رمز تصادفی ساخته می‌شود. رمز در لاگ چاپ **نمی‌شود**؛ با این دستور بخوانید:

```bash
docker compose exec subhub cat /app/data/initial-admin.txt
```

- **پورت**: اگر ۸۰۰۰ روی سرور اشغال است، در `.env` مقدار `PORT=8080` (یا هر پورت آزاد) بگذارید؛ داشبورد روی `http://IP:PORT/dashboard/` است.
- `PUBLIC_BASE_URL` خالی = `http://localhost:PORT`. برای لینک اشتراک درست، آن را روی آدرس واقعی (`http://IP:PORT` یا `https://دامنه`) بگذارید و `docker compose up -d` را دوباره بزنید.
- شبکهٔ کند/ایران: در `.env` مقدار `NPM_REGISTRY=https://registry.npmmirror.com` (و در صورت نیاز `PIP_INDEX_URL`) را بگذارید. تایم‌اوت و retry پیش‌فرض بالاست.
- سلامت: `/health` و `/api/health`؛ داشبورد: `/dashboard/`؛ مستندات خصوصی: پایین‌تر.

### رمز مدیر

مدیر اولیه فقط وقتی ساخته می‌شود که وجود نداشته باشد؛ تغییر `INITIAL_ADMIN_PASSWORD` در `.env` بعد از ساخته شدن اثری ندارد. برای ریست رمز:

```bash
docker compose exec subhub python -m cli reset-admin-password --username admin
```

### قفل ورود

۵ تلاش ناموفق برای هر ترکیب IP+نام‌کاربری = ۱۵ دقیقه قفل (شمارنده در حافظه است). برای پاک کردن: `docker compose restart subhub`. فقط برای تست: `LOGIN_RATE_LIMIT_ENABLED=false`.

### HTTP یا HTTPS

احراز هویت با توکن Bearer است (کوکی استفاده نمی‌شود)، پس روی HTTP ساده هم کار می‌کند. اما در اینترنت عمومی رمز و توکن بدون رمزگذاری می‌رود؛ برای استفادهٔ واقعی پشت HTTPS (`deploy/Caddyfile.example` یا `deploy/nginx.conf.example`) بروید.

## منوی ترمینال

دستور `parvmarz` (توسط install.sh نصب می‌شود؛ یا داخل پوشهٔ پروژه `bash parvmarz.sh`) منویی دارد برای: وضعیت، لاگ، استارت/استاپ/ری‌استارت، آپدیت، ویرایش `.env`، تغییر پورت/آدرس، ریست رمز مدیر، نمایش رمز اولیه، پاک کردن قفل ورود، بکاپ، بیلد مجدد و حذف.

## اجرای توسعه

Python 3.12 یا جدیدتر:

```bash
python -m venv .venv
. .venv/bin/activate
pip install -e '.[test]'
cp .env.example .env
subhub-cli init-db
subhub-cli admin-create

```

## قابلیت‌های موجود

- مدل‌های Admin، Panel، PanelInbound، Service، ServiceItem، User، UserPanelAccount، UserTemplate، UsageLog، AuditLog، SyncTask و Setting.
- احراز هویت JWT، هش رمز bcrypt، ابطال توکن‌های مدیر پس از تغییر رمز، قفل موقت تلاش‌های ورود و رمزنگاری Fernet برای اعتبارنامهٔ پنل.
- API پایه برای مدیریت پنل، سرویس، مدیر، کاربر، قالب، عملیات گروهی، آمار، audit و تنظیمات.
- ایجاد تسک Outbox در تغییرات کاربر، retry با backoff، worker دوره‌ای، پایش سلامت پنل، همگام‌سازی مصرف و تشخیص انقضا/محدودیت.
- HMAC برای لینک اشتراک؛ اعتبارسنجی نسخهٔ توکن پیش از استفاده از کش؛ کش کوتاه‌مدت در حافظه و دیتابیس؛ stale-if-error برای لینک‌های بالادستی.
- ادغام و حذف لینک‌های تکراری و خروجی اولیهٔ V2Ray، Clash و sing-box.
- رابط React دوزبانهٔ پایه با فهرست کاربران، فیلترها، ایجاد کاربر، عملیات سریع، پنل‌ها و سرویس‌ها.
- Docker چندمرحله‌ای، Compose، Alembic، CLI، بکاپ چرخشی SQLite، مثال‌های Caddy/Nginx و CI.

## درایورها، طرح دسترسی و نمایندگی

درایورها از قرارداد مشترک `PanelDriver` استفاده می‌کنند و قابلیت‌ها را در `capabilities` اعلام می‌کنند. APIهای مدیریتی پنل، قابلیت‌های هر اتصال را از مسیر `/api/panels/{panel_id}/capabilities` برمی‌گردانند. `AccessPlan` فقط منابع از قبل موجود را انتخاب می‌کند: `inbounds` برای Marzban/Marzdar/Marzyar، `service_id` برای Rebecca و `group_ids` برای PasarGuard. هیچ درایوری API ساخت/ویرایش اینباند، هاست، نود یا تنظیمات Xray را فراخوانی نمی‌کند.

برای هر نمایندهٔ Jinx Data می‌توان از `PUT /api/admins/{admin_id}/panel-access` اعتبارنامهٔ ادمین/کلید اختصاصی آن پنل را تنظیم کرد. رمز در جدول `admin_panel_access` به‌صورت رمزنگاری‌شده ذخیره می‌شود و در پاسخ فهرست یا لاگ نمایش داده نمی‌شود. کاربر غیر-sudo بدون نگاشت اختصاصی به اعتبارنامهٔ سراسری پنل سقوط نمی‌کند؛ تسک با خطا متوقف می‌شود تا دسترسی نماینده ناخواسته افزایش پیدا نکند. پیکربندی legacy پنل برای کارهای بدون مالک یا مدیر `sudo` حفظ شده است.

محدودیت‌های محلی نماینده (تعداد کاربران، حجم هر کاربر، حجم مجموع، روزهای انقضا و مجازبودن حجم/انقضای نامحدود) در API کاربران Jinx Data بررسی می‌شوند. مجوزهای `app/core/permissions.py` نیز برای عملیات مشاهده/ساخت/ویرایش/حذف/ریست/ابطال اشتراک/فعال‌سازی پلن بعدی اعمال می‌شوند. اعتبارنامه‌های رمزنگاری‌شدهٔ اختصاصی را از طریق API مدیریت نمایندگان تنظیم کنید؛ هر نماینده باید در پنل مقصد به یک ادمین/کلید با کمترین دسترسی لازم نگاشت شود.

### وضعیت پیاده‌سازی قابلیت‌ها

علامت **کد شده** به‌معنی وجود منطق درایور است، نه تأیید روی سرور واقعی. **نیازمند تأیید** یعنی مسیر/شِما/رفتار به نسخهٔ واقعی پنل وابسته است و باید با OpenAPI همان نصب بررسی شود. **پشتیبانی نمی‌شود** یعنی در این adapter قابلیت برای UI غیرفعال اعلام می‌شود.

### تست و موارد نیازمند تأیید

تست‌های mock صرفاً قرارداد و رفتار محلی درخواست‌ها را پوشش می‌دهند؛ هیچ اتصال زنده‌ای به Marzban، Marzdar/Marzyar، PasarGuard یا Rebecca در محیط توسعه انجام نشده است. OpenAPI و کد منبع عمومی فعلی Rebecca برای مسیرهای عمومی ادمین و مصرف ادمین بررسی شده، اما نصب واقعی ممکن است نسخه/تغییرات متفاوت داشته باشد. برای پذیرش تولیدی باید روی نسخه‌های نصب‌شدهٔ مقصد، `/openapi.json` یا Swagger بررسی شود؛ به‌ویژه endpointهای فهرست اینباندها و قالب‌های PasarGuard، رفتار اختصاصی Marzdar/Marzyar و مسیر محدودیت سرویس ادمین Rebecca که وابسته به نسخه است. فایل‌های مرجع `Rebecca-master.zip` و `Marzdar-master.zip` در ورودی همین اجرای پروژه موجود نبودند؛ schema محلی Marzdar از فایل منبع استخراج نشده است.

## امنیت عملیاتی

کلیدهای `.env` را commit نکنید. در محیط تولید، HTTPS، CORS محدود، کلیدهای مستقل و تصادفی، پشتیبان‌گیری خارج از سرور و دسترسی محدود به `/docs` را تنظیم کنید. پیش از استفادهٔ واقعی، درایورها و خروجی اشتراک را با پنل و کلاینت واقعی تست کنید.


### وضعیت اتصال PasarGuard (بازبینی مستندات V5)

- گروه‌ها مجوز دسترسی به اینباندها و هاست‌ها را تعیین می‌کنند؛ در Jinx Data فقط `group_ids` به کاربر اختصاص داده می‌شود و خود گروه/اینباند/هاست ساخته یا ویرایش نمی‌شود. گروه‌های غیرفعال نیز در فهرست نگه داشته می‌شوند تا رابط کاربری وضعیت واقعی را نمایش دهد.
- مسیرهای مستند عملیات گروهی: `POST /api/groups/bulk/add` و `POST /api/groups/bulk/remove` با فیلترهای `group_ids`، `users`، `admins` و `has_group_ids`.
- ایجاد گروهی از قالب از مسیر `POST /api/users/bulk/from_template` پشتیبانی می‌شود. شمای قالب و رفتار دقیق فیلدها باید با نسخهٔ نصب‌شده تطبیق داده شود.
- تاریخ انقضای `0` به معنی نامحدود بودن است. برای تغییرهای گروهی، حالت `dry_run` صرفاً پیش‌نمایش محلی است و پیش از اجرای واقعی، کاربران هدف خوانده و اعتبارسنجی می‌شوند.
- مستندات عمومی PasarGuard مسیرهای API را توصیف می‌کند، اما اتصال به یک نمونهٔ واقعی و تأیید سازگاری نسخه انجام نشده است. مسیرهای قالب‌های تکی، احراز هویت API key و فیلترهای فهرست کاربران باید روی نسخهٔ مقصد آزمایش شوند؛ این قابلیت‌ها برای نسخهٔ ناشناخته تضمین‌شده نیستند.

## اکانت من، رنگ‌ها و ورود دو مرحله‌ای

- منوی کناری (دکمهٔ منو بالای صفحه) ← **اکانت من**: حجم کل، مصرف‌شده، باقی‌مانده، حجم قابل تخصیص، تعداد کاربران، سقف‌ها و انقضای اکانت ادمین (برای همهٔ ادمین‌ها).
- **پالت رنگ** (همان صفحه یا دکمهٔ پالت رنگ بالای صفحه): رنگ اصلی و رنگ پس‌زمینه را با انتخابگر، کد HEX یا اسلایدر Hue/Saturation/Lightness بسازید؛ بقیهٔ رنگ‌ها خودکار هماهنگ می‌شوند. تم، زبان و رنگ‌ها هم در مرورگر و هم روی حساب ادمین ذخیره می‌شوند و با رفرش، خروج و ورود پاک نمی‌شوند.
- **2FA گوگل** (اختیاری): اکانت من ← احراز هویت دو مرحله‌ای ← QR را در Google Authenticator اسکن کنید و کد را تأیید کنید. ۸ کد بازیابی یک‌بارمصرف فقط همان لحظه نمایش داده می‌شود. هنگام ورود بعد از رمز، کد ۶ رقمی خواسته می‌شود.
- گم شدن گوشی: مدیر اصلی از تب ادمین‌ها «ریست 2FA» را می‌زند، یا روی سرور:

```bash
docker compose exec subhub python -m cli disable-2fa --username admin
```

(در منوی `parvmarz` هم گزینهٔ ۱۶ است.)

## اینباندها

همگام‌سازی پنل فقط **اینباندها** را نمایش و برای انتخاب در سرویس‌ها نگه می‌دارد. سرویس‌های Rebecca و گروه‌های PasarGuard به ادمین نشان داده نمی‌شوند؛ چون آن پنل‌ها بدون آن‌ها کاربر نمی‌سازند، برنامه موقع ساخت کاربر خودش سرویس/گروهی را که اینباندهای انتخاب‌شده را پوشش می‌دهد پیدا می‌کند. بعد از آپدیت یک‌بار روی هر پنل «همگام‌سازی» بزنید.



## کلید API و مستندات خصوصی (برای ربات‌های نمایندگان)

- ساخت کلید: نماینده با ورود عادی `POST /api/admin/api-keys` (یا مدیر اصلی `POST /api/admins/{id}/api-keys`) با `{"name":"bot","expire_days":90}`. کلید کامل (`pmk_...`) فقط یک‌بار نمایش داده می‌شود؛ حداکثر ۵ کلید فعال برای هر ادمین. برای مدیر اصلی (sudo) کلید صادر نمی‌شود.
- استفاده: هدر `X-API-Key: <key>` یا `Authorization: Bearer <key>`. کلید دقیقاً همان دسترسی‌ها و سهمیه‌های ادمین صاحبش را دارد (ادمین معلق/غیرفعال = کلید رد می‌شود) و نمی‌تواند رمز، 2FA یا کلیدها را مدیریت کند. ابطال: `DELETE /api/admin/api-keys/{id}`.
- مستندات: `GET /api/docs/openapi.json` و `GET /api/docs/api.md` فقط با توکن/کلید معتبر؛ مدیر اصلی اسکیمای کامل و نماینده فقط مسیرهای نماینده را می‌بیند.
- خروجی آفلاین برای دادن خصوصی به نمایندگان: `python -m cli export-openapi ./openapi` ← `agent.json` و `api-fa.md` (به نماینده بدهید) و `openapi.json` (کامل، فقط برای خودتان).
- `/docs` و `/openapi.json` عمومی به‌صورت پیش‌فرض خاموش است (`OPENAPI_ENABLED=false`).
